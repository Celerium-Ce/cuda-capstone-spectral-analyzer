# GPU Specialization Capstone — Batch Audio Spectral Analyzer

GPU Specialization capstone project. A GPU-accelerated batch audio
pipeline that computes a short-time Fourier transform (STFT) for every
mono WAV file in an input directory — turning each file's time-domain
waveform into a frequency-over-time spectrogram — and writes the result
as a CSV file, in a single run of the program.

## What this project does and why

The capstone rubric asks for real GPU computation applied to either "a
lot of small pieces of data (signal input arrays over time)" or "a few
large pieces of data (images/videos)," with a CLI, build files, and proof
that the program actually ran. This project leans into the first option
explicitly: every input file is sliced into hundreds of overlapping,
sub-second windows (STFT frames), and all of them are scored on the GPU
in the same run.

- Uses a **hand-written CUDA kernel** for framing and windowing
  (`src/window_kernel.cu`): one GPU thread block per STFT frame, one
  thread per sample in that frame, applying a Hann window to taper each
  frame's edges before the FFT.
- Uses **cuFFT** (`cufftExecR2C`, batched) for the Fourier transform
  itself — the rubric calls out GPU libraries as the preferred way to do
  standard, well-optimized operations like an FFT, rather than
  hand-rolling one.
- Uses a second **hand-written CUDA kernel** for the complex-to-magnitude
  conversion (`src/magnitude_kernel.cu`), so the project demonstrates
  genuine kernel design on both sides of the library call, not just a
  single library call dressed up as "GPU work."
- Processes the **entire input directory in one invocation**, round-robin
  across multiple CUDA streams with pinned host buffers, so transfers and
  compute for different files overlap instead of serializing — the same
  "at scale" batching approach used in this specialization's CUDA at Scale
  course project, now applied to a different domain (audio instead of
  images) and a different GPU library (cuFFT instead of NPP).

## Build

Requires the CUDA Toolkit (`nvcc`) with cuFFT (standard in any CUDA
Toolkit install) on `PATH`/`LD_LIBRARY_PATH`, and a CUDA-capable GPU.

```bash
make
```

Produces `bin/spectral_analyzer`. The Makefile's `ARCHES` variable targets
compute capabilities 5.2 through 8.6 by default; override it for other
GPUs, e.g.:

```bash
make ARCHES="-gencode arch=compute_86,code=sm_86"
```

## Dataset

`data/input/` contains 18 synthetic mono 16-bit PCM WAV files (16 kHz,
2 seconds each): pure tones, linear frequency chirps, two-tone mixtures,
tone-plus-noise, and pure white noise, generated by
`data/generate_signals.py`. Synthesizing the dataset locally — rather than
depending on a remote audio archive — keeps the project runnable with no
network access at build or grading time. Each tone file's filename states
its injected frequency (e.g. `tone_0440hz.wav`), so a reviewer can check
the program's output spectrogram against a known answer instead of having
to trust it blindly. Regenerate, or change which tones/chirps are
included, with:

```bash
python3 data/generate_signals.py [num_tone_files]
```

## Run

```bash
./bin/spectral_analyzer --input data/input --output output --log logs/run.log
```

or, to build and run in one step with a timestamped log file:

```bash
./run.sh
```

### CLI options

| Flag             | Default        | Description                                   |
|------------------|-----------------|------------------------------------------------|
| `--input DIR`    | `data/input`   | Directory of input `.wav` files                 |
| `--output DIR`   | `output`       | Directory to write spectrogram `.csv` files      |
| `--log FILE`     | `logs/run.log` | Path to write the run log                         |
| `--frame-size N` | `1024`         | STFT window length in samples (must be <= 1024)    |
| `--hop-size N`   | `512`          | STFT hop length in samples (overlap = frame - hop)  |
| `--streams N`    | `4`            | Number of concurrent CUDA streams                    |
| `--limit N`      | (all)          | Process at most `N` files (useful for a smoke test)   |
| `-h`, `--help`   |                | Print usage and exit                                   |

## Algorithm, per file

1. Read the WAV file's samples into a pinned (page-locked) host buffer,
   normalized to `[-1, 1]`.
2. Asynchronously copy host-to-device on a round-robin CUDA stream.
3. `WindowKernel` (`src/window_kernel.cu`): one thread block per STFT
   frame, one thread per sample. Each block slices out a `frame_size`
   window starting `hop_size` samples after the previous one
   (zero-padding past the end of the signal) and multiplies it by a Hann
   window, writing directly into the layout cuFFT's batched plan expects.
4. `cufftExecR2C`, batched over every frame in one call, bound to that
   stream via `cufftSetStream`: real time-domain frames in, complex
   frequency-domain spectra out.
5. `MagnitudeKernel` (`src/magnitude_kernel.cu`): a grid-stride loop over
   every complex bin, converting it to magnitude in decibels
   (`20 * log10(|z| + epsilon)`), which is both easier to eyeball in a CSV
   and closer to how the information would actually be used (e.g. for a
   spectrogram plot).
6. Asynchronously copy device-to-host and write the result as a CSV:
   a header row of bin center frequencies (Hz), then one row per frame
   labeled with that frame's start time (s).

The program logs per-file timing, frame/bin counts, plus aggregate
wall-clock time and throughput (frames/sec) for the whole batch to both
stdout and `--log`.

## Proof of execution

`output/*.csv` (18 spectrograms) and `logs/run_20261110_160327.log` are
committed in this repo from a real run on an **NVIDIA L4** GPU in the
Coursera lab: all 18/18 files processed successfully, 1098 STFT frames
computed in total, 0.96 ms of summed per-file GPU time against 2.6 s of
wall-clock (see "cuFFT plan overhead" in lessons learned below for why
those two numbers are so far apart — it's a real finding, not a bug).

**Verified against the sanity check below:** `output/tone_0440hz.csv`'s
loudest bin, averaged across its 61 frames, lands at 437.5 Hz (the bin
closest to the injected 440 Hz) at 43.6 dB, against a noise floor around
-115 dB.

**Sanity-checking the output yourself:** for any `tone_NNNNhz.wav` file,
the loudest bin in its output CSV should sit at (or one bin away from)
the frequency named in the filename.

```bash
python3 -c "
import csv
with open('output/tone_0440hz.csv') as f:
    reader = csv.reader(f)
    header = next(reader)
    freqs = [float(x) for x in header[1:]]
    sums = [0.0] * len(freqs)
    count = 0
    for row in reader:
        for i, v in enumerate(row[1:]):
            sums[i] += float(v)
        count += 1
    avg = [s / count for s in sums]
    peak_i = avg.index(max(avg))
    print('peak frequency:', freqs[peak_i], 'Hz (expected close to 440)')
"
```

This matches an equivalent NumPy STFT prototype run before writing the
CUDA code (see "Toolchain note" below): a synthetic 1000 Hz tone's
spectrogram peaked in the exact bin `1000 Hz` maps to, about 48 dB above
a noise floor around -114 dB.

**Toolchain note:** this repository was authored on a Windows machine
with no CUDA Toolkit (`nvcc`) installed (it has an NVIDIA GPU, but lacks
the toolkit), so the code itself could not be built there. It was instead
built and run on a standard CUDA Linux environment — the Coursera lab
terminal, producing the committed `output/` and `logs/` artifacts above.
To reproduce:


## Lessons learned / design notes

- **cuFFT plan overhead dominates at this scale.** The real lab run logged
  only 0.96 ms of *summed per-file GPU time* across all 18 files, but 2.6
  seconds of wall-clock time for the whole batch. The gap is
  `cufftPlan1d`/`cufftDestroy`: they run once per file, outside the timed
  `cudaEvent` window, and plan creation does real host-side setup work
  (picking an FFT factorization strategy, allocating cuFFT's internal
  scratch space) that costs far more than the window+FFT+magnitude kernels
  themselves do once the plan exists. A clear next step: cache one plan
  per distinct `(frame_size, num_frames)` pair and reuse it across files
  that share those dimensions, instead of creating and destroying one per
  file — all 18 synthetic signals here are the same length, so a single
  cached plan would have covered the entire batch.
- `cufftPlan1d(..., CUFFT_R2C, num_frames)` treats `num_frames` back-to-back
  1D transforms as one batched plan over contiguous memory, which matches
  the windowing kernel's output layout exactly (`num_frames x frame_size`,
  row-major) with no extra `cufftPlanMany` advanced-layout parameters
  needed — the simpler API was sufficient once the kernel's output layout
  was designed to match it, rather than the other way around.
- `frame_size` is capped at 1024 on purpose: the windowing kernel launches
  one thread block per frame with one thread per sample, and 1024 is the
  common hardware limit on threads per block, so every frame fits in a
  single block with no inner stride loop needed.
- Magnitude is converted to decibels on the GPU (`MagnitudeKernel`) rather
  than in the CSV-writing code on the host: it's exactly the kind of
  "elementwise work over a lot of small pieces of data" the rubric is
  looking for, and it means the host only ever deals with numbers that
  are already in a directly-plottable unit.
- Verifying the STFT math (frame count formula, frequency-bin mapping,
  that an injected tone actually shows up where it should) with a plain
  NumPy prototype first — before writing a single line of CUDA — caught
  an off-by-one in the frame-count formula early, on a machine that has
  no `nvcc` to catch it via a failed build instead.
- WAV parsing walks RIFF chunks generically (skipping anything that isn't
  `fmt `/`data`, honoring the mandatory word-alignment padding) rather
  than assuming the canonical 44-byte header, since real-world WAV
  encoders routinely insert extra chunks (e.g. `LIST`) before `data`.
